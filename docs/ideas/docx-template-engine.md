# DocxForge — Python Docx-шаблонизатор

## Problem Statement

Как сделать так, чтобы сотрудник отдела, имея десятки типов документов и разрознённые таблицы с данными, получал готовый .docx за пару кликов — без ручного ввода, без расхождения стилей и без программирования при добавлении нового типа документа?

## Recommended Direction

Десктопное приложение (PyQt/PySide + python-docx) с собственным простым DSL для разметки шаблонов прямо в .docx. Шаблон — главный источник правды: движок сканирует его и автоматически строит GUI-форму. Конфиг — минимальный YAML рядом с шаблоном. Пакетная генерация и константы задаются через GUI-диалог, а не через конфиг.

Ключевое архитектурное решение — текстовые плейсхолдеры {{ }} в docx со склейкой XML-ран (а не Content Controls / SDT). Это даёт простоту создания шаблонов для нетехнических пользователей, но несёт технический риск: склейка ран может ломать форматирование на сложных шаблонах. Поэтому **прототип склейки — первый артефакт**, до написания остального. Если склейка не работает на >20% реальных шаблонов — план отката: миграция на SDT.

DSL спроектирован по принципу «одна конструкция = один смысл»: @ = таблица, . = столбец, [ ] = поиск, {# } = цикл, image: = картинка. 10 правил, ноль угадываний. Парсер — на pyparsing/lark, не руками.

## Key Assumptions to Validate

- [ ] **Склейка XML-ран работает на реальных шаблонах.** Протестировать на 10 шаблонах с форматированием (жирный внутри плейсхолдера, курсив, merged cells). Если >20% ломаются → план отката на SDT.
- [ ] **Нетехнический сотрудник может разметить шаблон по инструкции.** Дать 2–3 сотрудникам инструкцию на 1 страницу, попросить написать {{ @клиенты.название }} в docx. Наблюдать, не помогать. Если не справляются → упростить DSL.
- [ ] **DSL покрывает 80%+ документов отдела.** Собрать список из 10–50 типов документов. Проверить, что каждое поле выражается через 10 конструкций DSL.
- [ ] **PyInstaller собирает рабочий .exe.** Протестировать на чистой Windows без Python. Если не работает → Investigate alternative (briefcase, nuitka).
- [ ] **Excel-данные достаточно структурированы.** Проверить 3–5 реальных Excel-файлов: одна строка заголовков, нет merged cells, нет пустых строк внутри данных.

## MVP Scope

### Порядок действий (по приоритету)

1. **Прототип склейки XML-ран** — проверить на 10 реальных шаблонах. Если не работает → пересмотреть фундамент.
2. **Тест DSL с пользователями** — инструкция на 1 страницу + наблюдение. Если DSL непонятен → упростить.
3. **Парсер DSL** (pyparsing/lark) — все 10 конструкций.
4. **Движок подстановки** — простые поля, @таблица.столбец, [N], [К=V], арифметика, агрегации, циклы, изображения.
5. **YAML-конфиг** — template, data, tables (алиасы), images, defaults, output.
6. **GUI: главное окно** — карточки шаблонов, drag-and-drop данных (QFileDialog для MVP).
7. **GUI: диалог генерации** — автопостроение формы из шаблона, переключатель «один/несколько», поля констант, выпадающие для @таблиц, выбор файлов для image:.
8. **Пакетная генерация** — итерация по таблице-драйверу, автоинкремент doc_number, фиксированные константы, прогресс-бар + отмена.
9. **Валидация шаблона** — кнопка «Проверить» → отчёт по полям, таблицам, опечаткам.
10. **PyInstaller .exe** — собирается и тестируется с первого спринта.

### Спецполя

- {{ today }}, {{ today:dd.MM.yyyy }} — текущая дата
- {{ doc_number }}, {{ doc_number:0001 }} — порядковый номер (автоинкремент в batch)

### DSL-конструкции (кратко)

| # | Конструкция | Смысл |
|---|---|---|
| 1 | {{ поле }} | Простое значение |
| 2 | {{ @таблица }} | Выбор строки из таблицы |
| 3 | {{ @таблица.столбец }} | Столбец из выбранной строки |
| 4 | {{ @таблица[N].столбец }} | Строка по номеру |
| 5 | {{ @таблица[К=V].столбец }} | Поиск по значению (VLOOKUP) |
| 6 | {{ today }}, {{ doc_number }} | Спецполя |
| 7 | {{ … * 1.2 }} | Арифметика (+, -, *, /), round(), len() |
| 8 | {{ sum(@таблица.столбец) }} | Агрегации (sum, count, max, min) |
| 9 | {# переменная in @таблица } … {#/} | Цикл по строкам |
| 10 | {{ image:имя }} | Изображение |

Полный справочник DSL и примеры шаблонов — в docs/ideas/docx-template-engine-dsl-examples.md.

## Not Doing (и почему)

- **Веб-интерфейс** — по требованиям: не веб-приложение
- **Маршруты согласования** — out of scope: не документооборот
- **Коллаборативное редактирование** — out of scope: не Google Docs
- **Jinja2 как DSL** — слишком сложен для нетехнических; Word ломает {{ }} по ранам так же, но синтаксис сложнее
- **Визуальный конструктор полей** — дорого в разработке; автогенерация формы из шаблона — достаточная альтернатива
- **Набор скриптов-шаблонов** — никто не будет поддерживать; нужен декларативный подход
- **AI-assisted генерация** — рано; недетерминированность неприемлема для юридических документов
- **Условия (if/else)** — MVP не требует; усложнит парсер; отложить до v2
- **Вложенные циклы** — MVP не требует; отложить до v2
- **Декартово произведение в batch** — риск взрыва документов; отложить до v2
- **Группировка по столбцу (batch group)** — v2
- **Диапазоны дат и чисел** — v2
- **Таблица рецептов (Excel с полным описанием каждого документа)** — v2
- **Ручной парсер DSL** — использовать pyparsing/lark, не писать парсер руками
- **Drag-and-drop зоны в GUI** — QFileDialog достаточно для MVP; drop-зоны — v2

## Open Questions

- Как обрабатывать форматирование внутри циклов? Копирование форматирования первой строки таблицы?
- Как обрабатывать ошибки? (поле не найдено, таблица пуста, ИНН не уникален) — выводить в GUI или лог?
- .xlsx и .xls, или только .xlsx? Нужна ли поддержка CSV?
- Как хранить счётчик doc_number между запусками? (файл состояния? вручную в конфиге?)
- Путь к данным — всегда файл, или нужна поддержка URL/сетевого пути?
- Нужна ли подпись/защита документа после генерации?
- Локализация GUI — только русский?
- Если склейка ран не работает на >20% шаблонов — каков объём миграции на SDT? Оценить до начала.
