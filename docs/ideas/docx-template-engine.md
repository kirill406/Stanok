# Python Docx-шаблонизатор

## Problem Statement

Как сделать десктопный GUI-инструмент, в котором сотрудник перетаскивает Excel и выбирает шаблон, а движок по YAML-конфигу подставляет данные, крутит циклы, считает агрегаты и вставляет картинки — и при этом добавление нового типа документа не требует написания кода?

## Recommended Direction

Десктопное приложение на PyQt/PySide с движком на python-docx. Шаблон — обычный .docx с собственным DSL-размеченными плейсхолдерами. Конфиг — минимальный YAML рядом с шаблоном. Пакетная генерация и константы задаются через GUI-диалог перед генерацией, а не через конфиг.

### Архитектура

- **Шаблон (.docx)** — главный источник правды. Содержит разметку DSL. Движок сканирует шаблон и строит форму GUI автоматически.
- **YAML-конфиг** — минимум: путь к данным, маппинг алиасов таблиц, пути к изображениям по умолчанию, предзаполнения полей. Всё остальное GUI выводит из шаблона.
- **Движок** — парсер DSL → склейка XML-ран → подстановка → вычисления → агрегации → циклы → изображения → запись .docx.
- **GUI** — PyQt/PySide. Карточки шаблонов → drag-and-drop данных → диалог генерации → результат.

### Принципы DSL

- Одна конструкция = один смысл. Движок не угадывает.
- @ = таблица, точка = столбец, [ ] = поиск, {# } = цикл, image: = картинка.
- 10 правил, каждое однозначное.

## Key Assumptions to Validate

- [ ] Word не ломает {{ }} плейсхолдеры чаще, чем склейка ран может восстановить — проверить на реальных шаблонах с форматированием (жирный, курсив внутри плейсхолдера)
- [ ] Пользователи смогут создавать/редактировать шаблоны с DSL-разметкой без программиста — провести тест с 2–3 реальными сотрудниками
- [ ] Собственный DSL покрывает 80%+ реальных документов отдела — собрать список из 10–50 типов документов и проверить выразительности DSL
- [ ] PyQt/PySide работает стабильно на целевых Windows-машинах без артефактов — протестировать на минимальной целевой конфигурации
- [ ] Производительность приемлема: генерация 200 документов за разумное время — замерить на типичном шаблоне

## MVP Scope

### Входит

1. **Парсер DSL** — склейка XML-ран + распознавание всех 10 конструкций
2. **Движок подстановки** — простые поля, таблицы, арифметика, агрегации, циклы, изображения
3. **YAML-конфиг** — минимальный: template, data, tables (алиасы), images, defaults
4. **GUI-диалог генерации** — автопостроение формы из шаблона, переключатель «один/несколько», поля ввода констант, выпадающие списки для @таблиц, выбор файлов для image:
5. **Пакетная генерация** — по строкам таблицы-драйвера, автоинкремент doc_number, фиксированные константы
6. **Спецполя** — today (с форматом), doc_number (с форматом и автоинкрементом)

### Не входит (MVP)

- Группировка по столбцу (batch group) — v2
- Декартово произведение таблиц — v2
- Диапазоны дат и чисел — v2
- Таблица рецептов (полное описание каждого документа в Excel) — v2
- Вложенные циклы (цикл внутри цикла) — v2
- Условия (if/else) — v2
- AI-assisted генерация — future
- Веб-интерфейс — out of scope
- Маршруты согласования — out of scope

## DSL v4 — полный справочник

### 1. Простая подстановка

```
{{ название }}
```

Значение берётся из данных. Не таблица — просто поле. Движок ищет в YAML → если нет, спрашивает в GUI.

### 2. Таблица: выбор строки

```
{{ @клиенты }}
```

@ = взять строку из таблицы. GUI покажет таблицу клиенты и предложит выбрать строку. Выбранная строка запоминается — все обращения к клиенты ниже используют ту же строку.

### 3. Таблица: столбец из выбранной строки

```
{{ @клиенты.название }}
{{ @клиенты.ИНН }}
```

Точка = разделитель «таблица.столбец». @ = таблица, после точки = столбец.

### 4. Таблица: конкретная строка по номеру

```
{{ @клиенты[3].название }}
```

Квадратные скобки — индекс строки. Третья строка, столбец «название».

### 5. Таблица: поиск строки по значению

```
{{ @клиенты[ИНН=7712345678].название }}
```

Найти строку, где столбец ИНН = 7712345678, взять название. Аналог VLOOKUP.

### 6. Спецполя

```
{{ today }}
{{ today:dd.MM.yyyy }}
{{ doc_number }}
{{ doc_number:0001 }}
```

Зарезервированные имена: 	oday, doc_number, 
ow, page. Распознаются по фиксированному списку — без угадываний.

### 7. Вычисления

```
{{ @клиенты.сумма * 1.2 }}
{{ @спецификация.итого + @спецификация.скидка }}
{{ round(@спецификация.итого, 2) }}
```

Операции: +, -, *, /. Функции: ound(), len().

### 8. Агрегации

```
{{ sum(@спецификация.цена) }}
{{ count(@спецификация) }}
{{ max(@спецификация.цена) }}
{{ min(@спецификация.цена) }}
```

Функции sum, count, max, min — с аргументом @таблица.столбец.

### 9. Циклы

```
{# строка in @спецификация }
{{ строка.наименование }}   {{ строка.количество }}   {{ строка.цена }}
{#/}
```

Внутри цикла строка — переменная текущей строки. Без @ = переменная цикла. С @ = таблица целиком.

### 10. Изображения

```
{{ image:логотип }}
{{ image:подпись:подпись.png }}
```

image: — явный префикс. Значение: имя из конфига или имя файла.

### 11. Алиасы (две строки из одной таблицы)

Шаблон:

```
{{ @заказчик.название }}
{{ @исполнитель.название }}
```

YAML:

```
tables:
  заказчик: клиенты
  исполнитель: клиенты
```

GUI покажет два списка выбора — оба мапятся на таблицу клиенты.

### 12. Пакетная генерация — через GUI

Пользователь нажимает «Сгенерировать» → модальный диалог:

- Переключатель: «Один документ» / «Несколько — по строкам таблицы»
- При выборе «Несколько»: выпадающий список таблиц-драйверов (из найденных @таблиц в шаблоне)
- @таблица-драйвер → «из очередной строки» (не список)
- @другие_таблицы → остаются выпадающими списками (фиксированный выбор)
- {{ номер }} → поле ввода + чекбокс «автоинкремент»
- Простые поля → фиксированные значения на все документы
- {{ today }}, агрегации, циклы → скрыты (движок обрабатывает автоматически)

GUI строит форму автоматически из шаблона. Никакого ручного описания полей в YAML.

## YAML-конфиг — минимум

```
# Минимум (80% случаев)
template: договор.docx
data: .

# Средний случай
template: договор.docx
data: данные/клиенты.xlsx
images: [logo.png, печать.png]

# Полный (крайние случаи)
template: договор.docx
tables:
  заказчик: клиенты
  исполнитель: контрагенты
data:
  клиенты: данные/клиенты.xlsx
  спецификация: данные/спецификация.xlsx
images:
  логотип: assets/logo.png
defaults:
  номер: 1
output: output/
```

## Not Doing (и почему)

- **Веб-интерфейс** — по требованиям: не веб-приложение
- **Маршруты согласования** — out of scope: не документооборот
- **Коллаборативное редактирование** — out of scope: не Google Docs
- **Jinja2 как DSL** — слишком сложен для неподготовленных пользователей; Word ломает {{ }} по ранам
- **Content Controls / SDT** — требует вкладки «Разработчик» в Word; порог входа выше; сложнее парсер
- **AI-assisted генерация** — рано; недетерминированность неприемлема для юридических документов; возможно в future
- **Набор скриптов-шаблонов** — никто не будет разрабатывать и поддерживать; нужен декларативный подход
- **Визуальный конструктор полей** — слишком дорого в разработке; DSL в docx + автогенерация формы — достаточно
- **Условия (if/else) в DSL** — MVP не требует; добавит сложность парсера; отложить до v2
- **Вложенные циклы** — MVP не требует; отложить до v2
- **Декартово произведение в batch** — риск взрыва количества документов; отложить до v2

## Open Questions

- Как обрабатывать форматирование внутри циклов? (шаблон строки таблицы — копирование форматирования первой строки)
- Как обрабатывать ошибки? (поле не найдено, таблица пуста, ИНН не уникален) — выводить в GUI или писать в лог?
- Нужна ли поддержка .xlsx и .xls, или только .xlsx?
- Нужна ли поддержка CSV наравне с Excel?
- Как хранить счётчик doc_number между запусками? (файл состояния? вручную в конфиге?)
- Путь к данным — всегда файл, или нужна поддержка URL/сетевого пути?
- Нужна ли подпись / защита документа после генерации?
- Локализация GUI — только русский, или возможен английский?
