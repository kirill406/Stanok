# Python Docx-шаблонизатор

## Problem Statement

Как сделать десктопный GUI-инструмент, в котором сотрудник перетаскивает Excel и выбирает шаблон, а движок по YAML-конфигу подставляет данные, крутит циклы, считает агрегаты и вставляет картинки — и при этом добавление нового типа документа не требует написания кода?

## Recommended Direction

Десктопное приложение на PyQt/PySide с движком на python-docx. Шаблон — обычный .docx с собственным DSL-размеченными плейсхолдерами. Конфиг — минимальный YAML рядом с шаблоном. Пакетная генерация и константы задаются через GUI-диалог перед генерацией, а не через конфиг.

### Архитектура

- **Шаблон (.docx)** — главный источник правды. Содержит разметку DSL. Движок сканирует шаблон и строит форму GUI автоматически.
- **YAML-конфиг** — минимум: путь к данным, маппинг алиасов таблиц, пути к изображениям по умолчанию, предзаполнения полей. Всё остальное GUI выводит из шаблона.
- **Движок** — парсер DSL → склейка XML-ран → подстановка → вычисления → агрегации → циклы → изображения → запись .docx.
- **GUI** — PyQt/PySide. Карточки шаблонов → drag-and-drop данных → диалог генерации → результат.

### Принципы DSL

- Одна конструкция = один смысл. Движок не угадывает.
- @ = таблица, точка = столбец, [ ] = поиск, {# } = цикл, image: = картинка.
- 10 правил, каждое однозначное.

## Phase 2: Стресс-тест и скрытые допущения

### Кластеры внутри решения

| Кластер | Суть | Главный риск |
|---|---|---|
| **A: DSL-ядро** | Парсер, склейка ран, подстановка, вычисления, циклы, агрегации, изображения | Технический — склейка ран, сложность парсера |
| **B: GUI-диалог** | Автопостроение формы из шаблона, batch-переключатель, константы | UX — интуитивность для нетехнических |
| **C: Пакетная генерация** | Итерация по таблице, автоинкремент, фиксированные константы | Корректность — обработка ошибок при массовой генерации |

### Стресс-тест по трём осям

#### A: DSL-ядро

- **User value:** Painkiller. Прямо решает проблему «время на документ с многих минут до пары кликов».
- **Feasibility:** Средняя. Три технических риска:
  1. **Склейка XML-ран** — решённая задача (docxtpl делает это годами), но на сложном форматировании (часть слова жирным, часть курсивом) склейка может потерять форматирование. Это главный технический риск MVP.
  2. **Собственный парсер DSL** — 10 конструкций + арифметика + агрегации = нетривиальная грамматика. Решение: использовать pyparsing или lark, не писать парсер руками.
  3. **Циклы в docx** — вставка строк в таблицу требует дублирования XML-элемента <w:tr> для каждой итерации. Вне таблиц — клонирование параграфов. Аккуратно, но выполнимо.
- **Differentiation:** Высокая. Собственный DSL с @-префиксом — не Jinja2, не Mustache, не handlebars. Простой, русский, ориентированный на табличные данные. Конкурентов с таким подходом на русском рынке — единицы.

#### B: GUI-диалог

- **User value:** Painkiller для нетехнических пользователей. Без GUI — инструмент только для тех, кто готов писать YAML. С GUI — для всего отдела.
- **Feasibility:** Средняя. PyQt/PySide — зрелый фреймворк, но:
  1. **Автопостроение формы** — парсер шаблона выдаёт список полей → GUI динамически создаёт виджеты. Несложно, но нужно продумать типы: текст → QLineEdit, дата → QDateEdit, таблица → QComboBox, image → QFileDialog.
  2. **Переключатель «один/несколько»** — при переключении меняется набор виджетов (таблица-драйвер исчезает из списков, появляется «из очередной строки»). Нужно корректно перестраивать форму.
  3. **Drag-and-drop** — QFileDialog достаточно для MVP; полноценные drop-зоны — приятность, не необходимость.
- **Differentiation:** Средняя. GUI сам по себе — не дифференциатор. Но **автопостроение формы из шаблона** — уникально. Пользователь не описывает поля вручную — GUI читает шаблон и спрашивает только то, что не может вывести.

#### C: Пакетная генерация

- **User value:** Painkiller для массовых рассылок. Приказы по 50 сотрудникам, договоры по 200 контрагентам — без batch это ручная работа на часы.
- **Feasibility:** Высокая. Итерация по строкам + подстановка + автоинкремент — алгоритмически простая задача. Основной риск — производительность: 200 документов может занять минуты, нужен прогресс-бар и кнопка отмена.
- **Differentiation:** Средняя. Mail merge — старая идея. Но интеграция batch в GUI-диалог с автопереключением полей — приятный UX.

### Аудит допущений

#### Must Be True (убийцы проекта, если неверны)

- [ ] **Склейка XML-ран работает на реальных шаблонах.** Если склейка ломает форматирование на 30%+ реальных шаблонов — проект мёртв в текущем виде. Путь отката: Content Controls (SDT), но это переписывание парсера. **Валидация: протестировать на 10 реальных шаблонах ДО написания движка.**
- [ ] **Пользователь способен написать {{ @клиенты.название }} в Word.** Если нетехнический сотрудник путается в @ и точке — DSL не работает, нужен визуальный конструктор (что исключено как дорогое). **Валидация: дать 2 сотрудникам инструкцию на 1 страницу, попросить разметить шаблон. Наблюдать, не помогать.**
- [ ] **Движок корректно обрабатывает .docx XML.** Формат docx — zip-архив с XML. Edge cases: merged cells, nested tables, sections, headers/footers. Если движок ломает форматирование на типовых документах — пользователи вернутся к ручному вводу. **Валидация: начать с простых шаблонов, добавлять поддержку сложных конструкций постепенно.**

#### Should Be True (важные, но не убийцы)

- [ ] **YAML-конфиг редактируется «админом шаблонов» без боли.** Если редактирование YAML вызывает страх — алиасы и defaults не будут использоваться. **Смягчение: GUI может предлагать редактирование конфига через форму, а не через текстовый файл.**
- [ ] **Excel-файлы структурированы достаточно.** Если данные — merged cells, многоуровневые заголовки, пустые строки — движок не сможет прочитать таблицу. **Смягчение: валидация данных перед генерацией + понятные сообщения об ошибках в GUI.**
- [ ] **PyQt/PySide не требует сложной установки.** Если пользователю нужно установить Python + PyQt + 5 зависимостей — порог входа слишком высок. **Смягчение: PyInstaller для одного .exe — обязательно с первого спринта.**

#### Might Be True (nice-to-have)

- [ ] Пользователи хотят хранить шаблоны централизованно (сетевая папка, общий диск). MVP — локальные файлы.
- [ ] Нужна поддержка .doc (старый формат). Маловероятно.
- [ ] Нужна мультиязычность GUI. Пока — только русский.

### Pre-mortem: проект провалился через 12 месяцев. Что пошло не так?

| # | Причина провала | Вероятность | Предотвращение |
|---|---|---|---|
| 1 | **Склейка ран ломает форматирование** — пользователи жалуются на «слетевшие шрифты», возвращаются к ручному вводу | Высокая | Протестировать на 10 реальных шаблонах ДО написания движка. Если >20% ломаются — переключиться на SDT. |
| 2 | **DSL слишком сложен для пользователей** — никто кроме автора не может создать шаблон | Средняя | Тест с 2 сотрудниками + инструкция на 1 страницу. Если не справляются — упростить DSL. |
| 3 | **Движок ломает сложные docx** (merged cells, колонтитулы, sections) — генерированные документы выглядят сломанными | Средняя | Начать с простых шаблонов. Чётко документировать ограничения. Добавлять поддержку сложных конструкций постепенно. |
| 4 | **Excel-данные — мусор** (merged cells, пустые строки, нечитаемые заголовки) — движок не может распарсить | Средняя | Валидация данных перед генерацией + понятные сообщения об ошибках в GUI. |
| 5 | **Установка слишком сложная** — Python + зависимости + PyQt = «я не программист» | Средняя | PyInstaller для одного .exe. Протестировать установку на целевой машине ДО релиза. |
| 6 | **Медленная генерация** — 200 документов за 10 минут, пользователи не ждут | Низкая | Прогресс-бар + кнопка отмена + замеры производительности на раннем этапе. |

### Честная оценка

**Сильные стороны:**
- Чёткая целевая аудитория и проблема (painkiller, не vitamin)
- DSL простой и однозначный — легче чем Jinja2, мощнее чем search-replace
- GUI строит форму автоматически — уникальная фича
- Пакетная генерация через GUI — простой UX для мощной функции
- YAML-минимализм — низкий порог для 80% кейсов

**Слабые стороны — честно:**
- Склейка XML-ран — единственная точка отказа всего проекта. Если она не работает на реальных шаблонах — нужно менять фундамент (на SDT), а это переписывание парсера.
- Собственный DSL = собственный парсер = собственные баги. Решение: pyparsing/lark вместо ручного парсера.
- Нет встроенной валидации шаблонов. Пользователь опечатался — узнает только при генерации. Нужен режим предпросмотра/валидации.

## Key Assumptions to Validate

- [ ] Word не ломает {{ }} плейсхолдеры чаще, чем склейка ран может восстановить — проверить на 10 реальных шаблонах с форматированием (жирный, курсив внутри плейсхолдера)
- [ ] Пользователи смогут создавать/редактировать шаблоны с DSL-разметкой без программиста — провести тест с 2–3 реальными сотрудниками, инструкция на 1 страницу, наблюдать без помощи
- [ ] Собственный DSL покрывает 80%+ реальных документов отдела — собрать список из 10–50 типов документов и проверить выразительность DSL
- [ ] PyQt/PySide работает стабильно на целевых Windows-машинах без артефактов — протестировать на минимальной целевой конфигурации
- [ ] Производительность приемлема: генерация 200 документов за разумное время — замерить на типичном шаблоне
- [ ] Склейка XML-ран не ломает форматирование на 30%+ реальных шаблонов — если >20% ломаются, переключиться на SDT
- [ ] Нетехнический сотрудник может написать {{ @таблица.столбец }} по инструкции — если нет, упростить DSL
- [ ] PyInstaller собирает рабочий .exe без ручной установки Python — протестировать на чистой Windows

## MVP Scope

### Входит

1. **Прототип склейки XML-ран** — первый артефакт, до написания остального движка. Проверить на 10 реальных шаблонах.
2. **Парсер DSL** — на базе pyparsing/lark + распознавание всех 10 конструкций
3. **Движок подстановки** — простые поля, таблицы, арифметика, агрегации, циклы, изображения
4. **YAML-конфиг** — минимальный: template, data, tables (алиасы), images, defaults
5. **GUI-диалог генерации** — автопостроение формы из шаблона, переключатель «один/несколько», поля ввода констант, выпадающие списки для @таблиц, выбор файлов для image:
6. **Пакетная генерация** — по строкам таблицы-драйвера, автоинкремент doc_number, фиксированные константы, прогресс-бар + отмена
7. **Спецполя** — today (с форматом), doc_number (с форматом и автоинкрементом)
8. **Валидация шаблона** — кнопка «Проверить шаблон» → отчёт по полям, таблицам, опечаткам
9. **PyInstaller .exe** — собирается с первого спринта, тестируется на чистой Windows

### Не входит (MVP)

- Группировка по столбцу (batch group) — v2
- Декартово произведение таблиц — v2
- Диапазоны дат и чисел — v2
- Таблица рецептов (полное описание каждого документа в Excel) — v2
- Вложенные циклы (цикл внутри цикла) — v2
- Условия (if/else) — v2
- Редактор YAML-конфига через GUI-форму — v2 (рассмотреть если YAML пугает пользователей)
- AI-assisted генерация — future
- Веб-интерфейс — out of scope
- Маршруты согласования — out of scope

## DSL v4 — полный справочник

### 1. Простая подстановка

```
{{ название }}
```

Значение берётся из данных. Не таблица — просто поле. Движок ищет в YAML → если нет, спрашивает в GUI.

### 2. Таблица: выбор строки

```
{{ @клиенты }}
```

@ = взять строку из таблицы. GUI покажет таблицу клиенты и предложит выбрать строку. Выбранная строка запоминается — все обращения к клиенты ниже используют ту же строку.

### 3. Таблица: столбец из выбранной строки

```
{{ @клиенты.название }}
{{ @клиенты.ИНН }}
```

Точка = разделитель «таблица.столбец». @ = таблица, после точки = столбец.

### 4. Таблица: конкретная строка по номеру

```
{{ @клиенты[3].название }}
```

Квадратные скобки — индекс строки. Третья строка, столбец «название».

### 5. Таблица: поиск строки по значению

```
{{ @клиенты[ИНН=7712345678].название }}
```

Найти строку, где столбец ИНН = 7712345678, взять название. Аналог VLOOKUP.

### 6. Спецполя

```
{{ today }}
{{ today:dd.MM.yyyy }}
{{ doc_number }}
{{ doc_number:0001 }}
```

Зарезервированные имена: today, doc_number, now, page. Распознаются по фиксированному списку — без угадываний.

### 7. Вычисления

```
{{ @клиенты.сумма * 1.2 }}
{{ @спецификация.итого + @спецификация.скидка }}
{{ round(@спецификация.итого, 2) }}
```

Операции: +, -, *, /. Функции: round(), len().

### 8. Агрегации

```
{{ sum(@спецификация.цена) }}
{{ count(@спецификация) }}
{{ max(@спецификация.цена) }}
{{ min(@спецификация.цена) }}
```

Функции sum, count, max, min — с аргументом @таблица.столбец.

### 9. Циклы

```
{# строка in @спецификация }
{{ строка.наименование }}   {{ строка.количество }}   {{ строка.цена }}
{#/}
```

Внутри цикла строка — переменная текущей строки. Без @ = переменная цикла. С @ = таблица целиком.

### 10. Изображения

```
{{ image:логотип }}
{{ image:подпись:подпись.png }}
```

image: — явный префикс. Значение: имя из конфига или имя файла.

### 11. Алиасы (две строки из одной таблицы)

Шаблон:

```
{{ @заказчик.название }}
{{ @исполнитель.название }}
```

YAML:

```
tables:
  заказчик: клиенты
  исполнитель: клиенты
```

GUI покажет два списка выбора — оба мапятся на таблицу клиенты.

### 12. Пакетная генерация — через GUI

Пользователь нажимает «Сгенерировать» → модальный диалог:

- Переключатель: «Один документ» / «Несколько — по строкам таблицы»
- При выборе «Несколько»: выпадающий список таблиц-драйверов (из найденных @таблиц в шаблоне)
- @таблица-драйвер → «из очередной строки» (не список)
- @другие_таблицы → остаются выпадающими списками (фиксированный выбор)
- {{ номер }} → поле ввода + чекбокс «автоинкремент»
- Простые поля → фиксированные значения на все документы
- {{ today }}, агрегации, циклы → скрыты (движок обрабатывает автоматически)

GUI строит форму автоматически из шаблона. Никакого ручного описания полей в YAML.

## YAML-конфиг — минимум

```
# Минимум (80% случаев)
template: договор.docx
data: .

# Средний случай
template: договор.docx
data: данные/клиенты.xlsx
images: [logo.png, печать.png]

# Полный (крайние случаи)
template: договор.docx
tables:
  заказчик: клиенты
  исполнитель: контрагенты
data:
  клиенты: данные/клиенты.xlsx
  спецификация: данные/спецификация.xlsx
images:
  логотип: assets/logo.png
defaults:
  номер: 1
output: output/
```

## Not Doing (и почему)

- **Веб-интерфейс** — по требованиям: не веб-приложение
- **Маршруты согласования** — out of scope: не документооборот
- **Коллаборативное редактирование** — out of scope: не Google Docs
- **Jinja2 как DSL** — слишком сложен для неподготовленных пользователей; Word ломает {{ }} по ранам
- **Content Controls / SDT** — требует вкладки «Разработчик» в Word; порог входа выше; сложнее парсер (резервный путь если склейка ран не работает)
- **AI-assisted генерация** — рано; недетерминированность неприемлема для юридических документов; возможно в future
- **Набор скриптов-шаблонов** — никто не будет разрабатывать и поддерживать; нужен декларативный подход
- **Визуальный конструктор полей** — слишком дорого в разработке; DSL в docx + автогенерация формы — достаточно
- **Условия (if/else) в DSL** — MVP не требует; добавит сложность парсера; отложить до v2
- **Вложенные циклы** — MVP не требует; отложить до v2
- **Декартово произведение в batch** — риск взрыва количества документов; отложить до v2
- **Ручной парсер DSL** — не писать парсер руками; использовать pyparsing или lark
