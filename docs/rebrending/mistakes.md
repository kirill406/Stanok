# Ошибки FirstAgent, мешавшие развивать продукт

Анализ кодовой базы `FA/FirstAgent` (36 файлов, ~7200 строк `src/`, 496 тестов)
перед чистым рерайтом в `Stanok`. Каждая ошибка — с ценой и выводом для
новой архитектуры (см. `arhitecture.md`, `layers.md`).

## 1. Три эпохи имени конфига без версионирования формата
Фиксированный `проект.docxforge` → именованные `<имя>.docxforge` → миграция
в Home с гибридным открытием. Каждое изменение молча ломало старые проекты;
версия при этом не менялась («можно ломать, версию не менять» — решение 002).
Цена: пользователи теряли открываемость проектов, тесты переписывались трижды.
Вывод: формат файлов — версионированный контракт с реестром миграций;
ломающее изменение = bump версии + миграция + запись в CHANGELOG.

## 2. Три реализации создания проектов
`schema.create_projects` (engine) + `create_projects_from_template` (flat) +
`create_nested_employee_projects` (nested) — один и тот же пайплайн тремя
путями с дрейфом семантики (счётчики чинились отдельно в B6 для каждого).
Цена: каждый багфикс приходилось портировать ×3; ревью не ловило расхождения.
Вывод: один use case = одна функция; flat/nested — параметры, не копии.

## 3. Цикл рендера — god-flow
`render_execute`/`render_loop`: выбор строк + резолв + XML + запись файлов +
resume в одном потоке (~400 строк). Разделить удалось только в самом конце
(Strangler, 003). Цена: любое изменение поведения требовало читать весь цикл;
параллельные агенты боялись его трогать.
Вывод: конвейер из стадий с явными DTO между ними (строки → Filling JSON →
docx); стадия не знает о соседях.

## 4. Утечки GUI в движок и наоборот
FillForm писал конфиги напрямую; движок знал про `проект.docxforge` по
фиксированному пути; глобальный `SETTINGS_FILE` мутировался тестами —
GUI-тесты писали в **реальный** `~/.docxforge` пользователя (флейк
`test_delete_recent_project`, мусор `T3*.docxforge`).
Цена: невоспроизводимые тесты, риск потери данных пользователя.
Вывод: движок не знает про файлы настроек и диалоги; состояние — через
инжектированные хранилища; тесты с изолированным Home (фикстура обязательна).

## 5. Excel как живая база данных
Чтение таблиц из 5+ мест (`Renderer._read_table_data`, `_resolve_row_*`,
`count_source_rows`, GUI-подсчёты), бинарные фикстуры в репозитории,
медленные GUI-тесты с тайминг-флейками.
Цена: тесты зависят от бинарников; рефакторинг чтения = правки везде.
Вывод: Excel читается **один раз** на границе (`tables → JSON`), дальше
только JSON; фикстуры — `tests/json/` (xlsx + эталон), а не `tests/documents/`.

## 6. Неявные контракты между фазами параллельной разработки
`getattr(bsc, 'skip_copy', False)` вместо поля схемы; сигнатура-заглушка
Phase 2 vs реализация Phase 3 (`max_projects` не на том месте);
возврат `(path, count)` vs `(path, emp, proj)`.
Цена: интеграция падала на стыках, чинили follow-up'ами.
Вывод: контракт фазы = типизированная сигнатура + тест контракта
(`test_m2_contract.py` — сохранить практику); `getattr`-утиная типизация
для межмодульных границ запрещена.

## 7. Dead code как норма
`setup_nested_*`, `write_nested_*`, `copy_data_folder`, обёртки-однодневки
(`resolve_field_values`), дубли резолверов (`resolve_fields` vs полный).
Удаляли в три захода (B10-тест, Phase 4, loop-switch).
Цена: новички (и агенты) правили мёртвый код; ревью пропускало.
Вывод: тест на мёртвый код (B10-практика) с первого дня; правило «одна
семантика — одна функция» в AGENTS.md.

## 8. Спеки и CHANGELOG задним числом
Спеки 000–002 писались после кода; CHANGELOG собран ретроспективно;
версия `0.1.0-alpha` не отражала ломающие изменения.
Цена: решения негде проверить; ревьюеры спорили «как было задумано».
Вывод: спека до кода (Status: draft → done), CHANGELOG ведётся в процессе,
ломающее = релизная заметка с путём миграции.

## 9. Невоспроизводимая сборка
`Станок.spec` в `.gitignore`: каждый собирал флагами по памяти, один раз
получили нерабочий exe (`ModuleNotFoundError`). Лечили документированием
команды — хрупко.
Вывод: спека сборки — в репозитории (флаги в CI-скрипте `scripts/build-exe.*`,
проверяемом как код); `.gitignore` для артефактов (`dist/`, `build/`), не для
рецепта.

## 10. Древний тулчейн по умолчанию
Python 3.8 32-bit: пины `PyQt5==5.15.11`, `pyqt5-qt5==5.15.2` ради win32-колёс,
невозможность современных зависимостей.
Вывод: в новом проекте Python 3.13 + `uv` с первого коммита (в `Stanok`
уже так); 32-bit не поддерживаем.

## 11. Логи куда попало
`docxforge.log` рядом с exe (в Program Files — read-only), потом в корне
репо, потом в Home. Три переезда за историю.
Цена: потерянные логи = невоспроизводимые баги у пользователей.
Вывод: единственное место с первого дня: `~/.stanok/` (логи, настройки,
миграции) + константа пути в одном модуле.

## 12. Глобальное состояние в синглтонах
`SETTINGS_FILE` на import-time, кэш путей шаблонов на инстансе без
инвалидации, `logging.basicConfig` в `run.py`.
Цена: тесты влияют друг на друга через глобалы; порядок запуска значим.
Вывод: состояние — параметры конструктора; import без side effects
(в `Stanok` уже правило AGENTS.md).
