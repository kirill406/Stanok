# SPEC.md — 002-stabilization (доводка продукта)

Status: draft. Branch: `spec-002`.

## Goal
Довести «Станок» до стабильного состояния: предсказуемое создание
генерируемых проектов, сохраняемые логи, отсутствие падений, контроль
копирования таблиц, защита от перезаписи, корректные счётчики.
Ранее готовое (мультивыбор папок, папка `Результат`, разрыв строки перед полем) —
сверить и зафиксировать как done с доказательством. Можно пожертвовать обратной совместимостью (версию при этом не менять).

## Блоки (непересекающиеся, для параллельной работы)

### B0 «Сверка готового»
Подтвердить и зафиксировать как done с доказательством (коммит + тест/поведение):
- Множественный выбор папок проектов (кнопка в главном окне, валидные папки —
  в недавние, остальные — в сводку).
- Папка вывода генерации — `Результат` (каталога `output` нет в коде и на диске).
- Разрыв строки (здесь обозначается как -) между текстом съезжает к заполняемому полю:
  `текст-текст{{поле}}` сейчас рендерится как `тексттекст-{{поле}}`. Это баг
  слияния run'ов в рендере, чинится как багфикс с регрессионным тестом
  (зарезервирован `renderer.py`, см. Non-overlap contract).
Gaps → отдельные follow-up задачи, не молчаливое закрытие.

### B1 «Генерируемые проекты»
- Шаблон docx в генерируемых проектах заполняется (предзаполнение как раньше,
  все поля переносятся в конфиг).
- Файл конфига именуется по названию самого проекта (`проект1` →
  `проект1.docxforge`) и создаётся рядом с `Данные/` и `Шаблоны/`
  (фиксированного `проект.docxforge` в генерируемых папках нет).
- При открытии программы конфиги `*.docxforge` рядом с `Данные/`/`Шаблоны/`
  (кроме обычного `проект.docxforge`) мигрируют: данные переносятся в
  `.docxforge/<имя>.docxforge` домашней папки (коллизия → `(1)`, `(2)`),
  исходник из папки удаляется.
- Открытие гибридное: резолвер (папка → именованный конфиг → Home-копия);
  сохранения пишутся обратно в открытый файл.
- Файл `проект.docxforge` именуется по названию самого проекта и сохраняется
  в подпапку `.docxforge` домашней папки пользователя (рядом с логами и
  настройками). Имя занято → переименование создаваемого файла по правилу
  B5 (`(1)`, `(2)`, …), существующее не трогаем. Тесты в реальный Home не
  пишут (fixture перенаправляет в tmp, tmp чистится сам).
- Документы из папок `шаблоны/` внутри генерируемых проектов заполнены данными,
  константы подставлены (проекты создаются предзаполненными, не пустыми).
- В окно заполнения шаблона добавляется секция «Поля шаблона для генерируемых
  проектов»: заданные в ней поля определяют отдельный шаблон файла
  `проект.docxforge` для генерируемых проектов.

### B2 «Логи»
- Общий лог приложения не теряется: пишется в файл в домашней папке
  пользователя (Home), переживает перезапуск программы.
- Путь и имя файла — константа в одном месте (без хардкода по коду).

### B3 «Падение из меню заполнения»
- Воспроизвести падение при создании из меню заполнения шаблонов, зафиксировать
  traceback в задаче.
- Исправить причину; добавить регрессионный тест, воспроизводящий сценарий.

### B4 «Исключение копирования»
- При генерации проектов у каждой таблицы чекбокс «Исключить копирование»
  (строка через `STRINGS`, без хардкода русского текста).
- Исключённые таблицы не копируются в папку `Данные/` генерируемого проекта;
  остальные копируются как раньше.

### B5 «Защита от перезаписи и недавние»
- Генерация из главного меню не перезаписывает файлы: если файл существует,
  создаваемый файл переименовывается (`файл (1)`, `файл (2)`, …).

### B6 «Счётчик при создании из генерации»
- Создание документов/проектов из генерации прибавляет счётчик так же, как
  обычная генерация.
- Сценарий покрыт регрессионным тестом (было/стало по значению счётчика).

## Non-overlap contract
Каждый блок работает только в своих файлах; чужие файлы не трогать.
Порядок захвата: B3 первым заявляет файлы по итогам traceback (до этого B1/B4
не коммитят в `form_dialog.py`); `renderer.py` зарезервирован за фиксом разрыва строки (B0).
- B0: чтение + фиксация; код — только фикс разрыва строки в `renderer.py` отдельной веткой.
- B1: `form_dialog.py` (секция), `config_collector.py`, `config_io.py`, `generate.py`
  (создание проектов), project I/O.
- B2: logging setup (`run.py`, модуль логов).
- B3: entry points окна заполнения (файлы — по traceback, заявляются первыми).
- B4: `batch_section.py`, `field_rows.py` (чекбокс таблицы), флаги копирования в `generate.py`
  (координация с B1 через мелкие коммиты: флаги и создание проектов — разные функции).
- B5: главное меню + recent storage (только чтение формата!) + переименование в engine.
- B6: engine counter path.
Конфликт по общему файлу → стоп, `git pull --rebase`, мелкий коммит, дальше.

## Acceptance
- Каждый блок: поведение проверено + тест (для B3, B5, B6 — обязательно;
  для GUI — pytest-qt либо ручной чек-лист, приложенный к задаче).
- `pytest tests/ -q` зелёный после каждого блока.
- Конвенции репо: `logging` вместо `print`, RU-строки через `STRINGS`,
  багфикс → регрессионный тест, коммит на задачу.
- Ломающие совместимость изменения (разрешены, версия не меняется) фиксируются
  записью в CHANGELOG `[Unreleased]`: что сломано и как мигрировать.

## Out of scope
- Фичи вне перечисленных блоков.
- Формат недавних проектов не меняется.
- CLI-паритет (отдельная работа, см. `docs/cli-gui-parity.md`).
